# Конечный ограниченный проход П5: узел и ведомости

```bash
python3 tools/node_lifecycle_0110/run_lifecycle.py --out /tmp/node_lifecycle
```

Это последний согласованный программный проход ограниченного П5 перед
проверкой в AutoCAD, а не новая инженерная веха или функция. Настоящие
`FrameNodeCommand.Node` (Create/Check), `FrameNodeRenderer`, `FrameNodeStore`
и `FacadeQuantityTableCommand.Run` выполняются в **одной Database** с теми
же реальными guards, источниками, движками и физическими паспортами
`LimitedPilotProbe`. Отдельный NodeCheckpoint отсутствует при прежнем
standalone запуске: C# удаляет невнедрённый partial hook.

Сценарий: N1 fresh → проект230→240, N1 stale → отмена диалога / отмена
точки / отказ сменившейся ПСК до записи → N1 сохраняет ссылки, transform,
исходный raw-паспорт, body и digests → N2 с отдельными owner/definition
fresh при выдаче, N1 stale. Последующее переиздание ведомостей и локальное
исключение правой зоны проходят на той же базе. Поздняя проверка таблицы
намеренно меняет проект до revision3: изменение сохраняется, обе схемы
становятся stale. Свежесть N2 не распространяется на этот поздний момент.

Схемы не входят в физическую ведомость: выполнены реальные PreviewImport
с generated_conflict и смешанная выборка зон/узлов с явными Unaccounted
позициями. В текущих физических отчётах12 плит,2ГП,6кронштейнов; шаблон
слоёв100+50мм, локальный просвет170−150=20мм не подтверждают монтаж/расчёт.

До подключения renderer воспроизведён дефект прежнего **адаптера**:
внутренний Line определения попадал также в ModelSpace. Исправлена только
модель принадлежности: OwnerId и регистрация AppendEntity в указанном
определении. Продукт Node не изменён. Проверены и заранее созданный
ModelSpace, и его ленивая инициализация. Команда воспроизведения:

```bash
python3 tools/node_lifecycle_0110/run_lifecycle.py --out /tmp/node_before --ownership-source docs/node_lifecycle_0110/before/QuantityCadDoubles.cs --expect-ownership legacy
```

Та же команда с `--expect-ownership fixed` обязана завершиться отказом.
Это проверяет чувствительность регрессии к исходной ошибке адаптера;
полного «до» прохода по неверной модели CAD не объявляем.

Результат: `manifest.json`, `node_command/result.json`, реальный Table
результат, исходные engine requests/responses,19 выдаваемых XLSX и
контрольные файлы сохранности. `native_result.node_scope` относится только
к унаследованному pure-сегменту; полное исполнение Node учитывается отдельно
в `node_command/result.json`. Три независимых oracle и все исполняемые входы
привязаны SHA256, четыре дословно извлечённых helper привязаны отдельно.
Запуск не зависит от истории Git или сети.

Счётчики снимаются сразу по возврате каждой Node-команды, до инспекции:
0 ModelSpace visits и0 дополнительных вызовов движков. Уже существующие
обходы ведомостей честно видят1/2 новых block references; внутренние
примитивы определения туда не попадают. Managed-время не является
измерением скорости живого AutoCAD.

Границы: scripted Editor/form, свойства CAD и операции хранения моделируются;
native display/сохранение-DWG/переоткрытие/COPY/SaveAs/Undo/rollback НЕ
ПРОВЕРЕНЫ. Commit/Dispose остаются no-op; проверяется лишь отказ до записи,
не откат частично созданного блока. Не заявлено равенство native цветов,
оформления/рендера и WinForms. Монтаж2В/расчёт3А/автоподбор BLOCKED.
После этого прохода новые искусственные стадии автоматически не открываются:
оставшийся список host-проверок передаётся на живой пилот.
