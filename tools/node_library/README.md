# Подготовка первого нативного динамического узла

`generate.py` выпускает **авторский AutoLISP для полного AutoCAD 2024 Windows**.
DWG создаётся только при выполнении этого LISP в AutoCAD: `-BEDIT`, `BPARAMETER`,
`BACTIONTOOL`, `-BVSTATE`, `BVSHOW`, `BSAVE`, `BCLOSE`. Linux-проверка не создаёт
нативного определения, не исполняет его вычислитель и не является живой приёмкой.

Публичный `fixtures/rectangles.json` содержит только обезличенные прямоугольники.
Это проверочный вход генератора, **не узел Вектор**. Исходные данные и подготовленный
LISP учебного Вектора находятся в
[приватной папке пилота](https://github.com/zinchenko-denis/atspec-testdata/tree/feat/vector1-node-pilot/node_library/vector1_2015_4_2_1).
Приватный LISP содержит геометрию входного JSON; не переносить его в публичный Git.

## Подготовить и проверить исходник

Из корня репозитория:

```bash
python3 tools/node_library/test_author.py
python3 tools/node_library/generate.py /private/vector1_2015_4_2_1_training.json /private/vector1_2015_4_2_1_training.lsp
```

Результат — UTF-8 LISP с SHA-256 исходного контракта и явной пометкой, что
нативного запуска ещё не было. Для обезличенного испытания вместо приватного JSON
можно передать `tools/node_library/fixtures/rectangles.json`.

## Один авторский запуск в AutoCAD

1. Открыть **новый, чистый, несохранённый** чертёж в полном AutoCAD 2024.
   Пустое пространство модели и отсутствие определения с таким именем проверяются
   до изменений. В существующем чертеже или открытом редакторе блока команда откажет
   до записи. Она не закрывает чужой редактор и не отменяет чужие команды.
2. `APPLOAD` — загрузить подготовленный `.lsp`, соблюдая обычные настройки доверия
   AutoCAD. Нужен Unicode AutoLISP (`LISPSYS` 1 или 2); скрипт не отключает защиту
   загрузки и не меняет профиль AutoCAD.
3. `ATFNATIVEBUILD` — выбрать **новое** имя DWG. Существующий файл не перезаписывается.
   Команда создаёт параметры/действия, два состояния видимости, затем пять вставок.
   Проверяет настоящую вычисленную геометрию, размеры и марки; меняет три вставки,
   сохраняет две, выполняет обратный переход, повтор и копирование через API.
   Только после этих проверок записывает маркер совместимости и сохраняет DWG.

Если очередная нативная команда оставляет непредусмотренный запрос, скрипт
прерывается. Он закрывает только собственный редактор, отменяет только свою группу
и восстанавливает изменённые настройки. Если сам AutoCAD отказал при очистке,
выводится явное сообщение: этот новый чертёж следует закрыть без сохранения.
Не использовать файл после сообщения об ошибке сохранения. Нативная работа этого
обработчика также требует проверки в AutoCAD; тесты Python проверяют его решения
о владении, а не реализацию `UNDO` внутри AutoCAD.

## Проверить результат инженеру

При загруженной DLL AFrame из соответствующего исходного кода:

- Открыть созданный DWG. У вставки должны быть **штатные** свойства
  `AFN_INSULATION`, `AFN_CLADDING_X`, `AFN_VARIANT` и линейные ручки.
- Авторский пример оставляет первые три вставки в B, две остальные в A.
  Сначала `ATFNODEEDIT`: ввести 100, 230, A, затем выбрать все пять — исходное состояние.
  Повторить команду: ввести 150, 280, B, затем выбрать рамкой только три вставки.
  Утеплитель, плита, размеры и дискретные детали/марки должны измениться;
  две невыбранные вставки — остаться прежними. Повтор тех же чисел не сдвигает базы.
- Вернуть три изменённые вставки в A через `ATFNODEEDIT` (100, 230, A).
  `ATFNODETEST`: выбрать все пять одинаковых A и ввести 150, 280.
  Проверка геометрии через AutoCAD API изменяет три вставки с первыми handles,
  сообщает их и откатывает результат; пользовательскую приёмку она не заменяет.
- Отдельно выполнить ручное редактирование Properties/ручками, отмену выбора,
  `COPY`, `UNDO`, сохранить, закрыть и открыть DWG. Эти действия не засчитываются
  за выполненные по результатам Python или одного чтения динамических свойств.
- `ATFNODEIMPORT` импортирует совместимое определение из библиотечного DWG;
  `ATFNODEDEMO` создаёт пять копий выбранной вставки для проверки. Чужое определение
  с совпавшим именем не заменяется автоматически.

Учебный пилот имеет отдельный `node_id=vector1_2015_type1_4_2_1_training`.
Его варианты: `V1_KR2_70_200_GP_40_40_1p2` и `V1_KR2_70_250_GP_60_40_1p2`.
Парные учебные данные: A — утеплитель 100, вынос 230; B — 150 и 280 мм.
Положение УК/ГП задано отдельно в каждом варианте. `AFN_CLADDING_X` двигает
плиту и связанные размеры, не вычисляет положение УК/ГП или длину кронштейна.
Условные пятки/гибы и непроверенный монтаж отмечены на изображении узла.

## Контракт входа и совместимость

JSON `schema=af_node_native_author/1` содержит:

- `node_id`, `version=1`, `block_name`, `units=mm`, `origin=[0,0]`, `provenance`;
- две строки `variants`; состояния `defaults` и `alternate` с тремя точными
  именами свойств; две горизонтальные `parameters` со `start`, `end`, `label`
  и обязательным `dimension_id` своего общего размера (`dim_insulation` и
  `dim_cladding` в учебном пилоте). Размер измеряет от стены исходное значение
  параметра; его действие stretch включает только подвижный конец, а нативная
  проверка сопоставляет измерение с текущим значением параметра;
- `entities` с уникальными `id`, `type` и необязательным `variant` (`null` — общие).
  Типы: line (`start/end`), polyline (`points/closed`), circle (`center/radius`),
  text (`position/height/text`), dimension (`p1/p2/line_point/height`), attribute
  (`position/height/tag/text/prompt`). Все точки — `[x,y]`, в миллиметрах;
- `actions`: `parameter`, `kind=stretch|move`, явные `entities`; для stretch —
  `frame=[[xmin,ymin],[xmax,ymax]]`. Один объект не включается дважды в действия
  одного параметра. Параметры, действия и владельцы не угадываются по размеру.

Числа проверяются на конечность и положительность; вынос больше утеплителя.
Это проверка графического ввода, не диапазон допуска изделия или несущая проверка.
Генератор не выводит формул монтажа и не создаёт инженерных характеристик.
Размеры явно получают масштаб измерения 1, десятичные единицы и пустые
текстовые замены/префиксы; настройки чужого DWT не должны менять их подпись.

В `ExtensionDictionary` **исходного динамического BlockTableRecord** записывается
XRecord `AF_NODE_LIBRARY`: `1=node_id`, `90=version`, затем пять полей с кодом `1`:
`AFN_INSULATION`, `AFN_CLADDING_X`, `AFN_VARIANT`, вариант A, вариант B.
Маркер читается обратно после записи. Имя определения само по себе не доказывает
совместимость; анонимный вычисленный блок не подменяет исходное определение.

## Почему выбран этот путь

Autodesk документирует [BPARAMETER](https://help.autodesk.com/cloudhelp/2024/ENU/AutoCAD-Core/files/GUID-E4460179-F0FC-4AC6-85D7-35B05D018D16.htm),
[BACTIONTOOL](https://help.autodesk.com/cloudhelp/2024/ENU/AutoCAD-Core/files/GUID-86B3A05A-B637-440D-8310-49915CB09BF2.htm)
и [вызов команд из AutoLISP](https://help.autodesk.com/cloudhelp/2024/ENU/AutoCAD-AutoLISP-Reference/files/GUID-1C989B35-2C5A-47EC-A0C9-71998EDFB157.htm).
[DynamicBlockReferenceProperty](https://help.autodesk.com/cloudhelp/2024/ENU/OARX-ManagedRefGuide/files/OARX-ManagedRefGuide-Autodesk_AutoCAD_DatabaseServices_DynamicBlockReferenceProperty.html)
даёт доступ к свойству существующей вставки, а не конструктор параметров/действий.
Непубличные объекты графа динамики, перерисовка обычных блоков и непроверенный
запуск Block Editor в Core Console здесь не используются.
