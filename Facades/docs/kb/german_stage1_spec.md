# ТЗ Германа на этап 1 (переписка 19.07, зафиксировано 18.07k)

Источник: переписка Дениса с Германом (главный конструктор направления).
Герман подтвердил модульную архитектуру («разбить на модули/блоки, которые
потом можно объединить») и описал воркфлоу первого модуля.

## Видение Германа

**Идеал (дальний):** программа, в которую загружаешь АР (планы, фасады,
сечения) → подсчитывает объёмы, выделяет в DWG зоны, которые считала,
и **делает развертки фасадов, которые не показаны в АР (ниши, боковые
стенки, потолки)**. Сам Герман оценивает это как нереальное для плагина
AutoCAD и сложное даже отдельным приложением.

**Реализм (этап 1):** «не обойтись без оператора-человека». Приложение к
AutoCAD, которое облегчает подсчёт на этапе КОММЕРЧЕСКИХ РАСЧЁТОВ,
разбиение на захватки, установка чётких границ для последующей раскладки.

**Скепсис:** «Первый этап самый сложный. Я не уверен, что мы его реализуем
из-за ОТСУТСТВИЯ СТАНДАРТОВ В ИСХОДНОЙ ПРОЕКТНОЙ ДОКУМЕНТАЦИИ. Но будем
пробовать. Как сделать всё остальное — я чётко понимаю».
(Позиция Дениса: «Попробуем всё же первый этап победить без ручного
контура» — автоматика. Наша стратегия остаётся: ручной инструмент сразу
= немедленная польза, автораспознавание поверх, итерациями на парах
«АР → готовый ВФ», которые Герман поищет.)

## Воркфлоу ручного режима (Герман, дословно по шагам)

1. Пользователь задаёт границы облицовки ЗАМКНУТЫМ КОНТУРОМ.
2. Запускает приложение:
   - 2.1 приложение просит выбрать контуры облицовки;
   - 2.2 запрашивает НАИМЕНОВАНИЕ облицовки (например «штукатурка по
     утеплителю 150 мм» или «керамогранит идальго 600х600») → программа
     создаёт СЛОЙ с этим именем и переводит выбранные контуры в этот слой;
   - 2.3 ШТРИХУЕТ каждый контур отдельно, ВЫЧИТАЯ из зоны окна и двери,
     запрашивая у пользователя тип и цвет штриховки;
   - 2.4 создаёт атрибут-текст с ПЛОЩАДЬЮ штриховки, размещает внутри
     контура;
   - 2.5 создаёт атрибут МАРКИРОВКИ контуров;
   - 2.6 в итоге делает ТАБЛИЦУ с площадью участков и ПОГОНАЖЕМ ОТКОСОВ
     И ОТЛИВОВ.

**Итог по Герману:** «таблицы с площадями + границы участков облицовки,
раскиданные по слоям + возможность выгружать площади и ДРОБИТЬ НА ЗАХВАТКИ
как угодно. Далее на основе этих участков — раскладка облицовки и
подсистема».

## Следствия для реализации (решения Логоса)

1. **Слой = носитель типа облицовки** (имя слоя = наименование облицовки).
   В `facade_zone/1` это ложится в `name`/`system` + `source.layer`;
   добавим поле `cladding` (строка наименования) при реализации C#-команды.
2. **Штриховка с островами — центральный артефакт:** HATCH по контуру зоны
   с вычетом контуров проёмов (island detection) даёт (а) визуальный
   результат на чертеже, (б) площадь нетто прямо из Hatch.Area —
   кросс-чек нашего движка (две независимые оценки площади!).
3. **Атрибуты на чертеже:** текст площади внутри контура + маркировка зоны
   (ID) — чертёж остаётся самодостаточным документом; наш JSON — снимок.
4. **Таблица площадей + погонажей (откосы, отливы)** — рисуется на чертеже
   (паттерн ATableSpec) и/или выгружается: прямой вход для СО/ВР.
   Погонажи по типам кромок проёмов — движок уже отдаёт периметры
   проёмов; надо разделить по типам (низ проёма = отлив, верх+бока =
   откос/отсечка) — доработка zone_report.
5. **Захватки = дробление участков ПОСЛЕ обсчёта, «как угодно»** — зона
   первична, захватка — группировка/разрез зон на этапе выгрузки. В
   формат добавим опциональный атрибут `zakhvatka` позже, когда Герман
   покажет, как дробит.
6. Развертки не показанных в АР поверхностей (ниши, боковые стенки,
   потолки) — отметить как отдельный будущий модуль (генерация разверток
   из планов+фасадов) — в бэклог, не этап 1.
7. Имя C#-команды (рабочее): **ATFZONE** — по паттерну ABlockGen: выбор
   полилиний → диалог наименования → слой/штриховка/атрибуты → JSON →
   движок → таблица. Движок `facade_zones.py` уже готов под это.
