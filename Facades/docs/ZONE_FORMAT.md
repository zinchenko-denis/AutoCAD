# Формат зоны фасада — `facade_zone/1`

Контракт блока A: зона = участок фасада, на котором проектируется НВФ или СФТК.
Один JSON-файл может нести одну зону (объект) или массив зон. Формат — вход
для `engine/facade_zones.py` (валидация + площади) и, дальше, для раскладки
НВФ (`nvf_layout`) и расчёта СФТК (`sftk_calc`). Источник зоны на этапе 1 —
ручная обводка полилинией в AutoCAD (C#-команда снимет геометрию в этот JSON);
позже тот же формат наполняет автораспознавание DWG/DXF и PDF-кросс-чек.

## Схема

```json
{
  "schema": "facade_zone/1",
  "id": "Z-01",
  "name": "Захватка в осях 1–5, южный фасад, 2 этаж",
  "facade": "Ю",
  "floors": "2",
  "base": "монолит",
  "system": null,
  "units": "mm",
  "outer": {
    "pts": [[0,0], [12000,0], [12000,3000], [0,3000]],
    "bulges": [0, 0, 0, 0]
  },
  "openings": [
    { "id": "W-01", "kind": "window",
      "poly": { "pts": [[1500,900], [3000,900], [3000,2400], [1500,2400]] } }
  ],
  "source": {
    "method": "manual",
    "file": "АР_дом1.dwg", "layer": "А-стены",
    "author": "Герман", "date": "2026-07-18"
  },
  "meta": {}
}
```

## Поля

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `schema` | `"facade_zone/1"` | да | версия формата |
| `id` | строка | да | уникальный идентификатор зоны в файле |
| `name` | строка | нет | человекочитаемое имя |
| `facade` | строка | нет | фасад/ориентация («Ю», «в осях А–Д»…) |
| `floors` | строка | нет | этаж(и): «2», «1-9», «техэтаж» |
| `base` | строка | нет | основание: «монолит», «кирпич», «газобетон»… (выбор типа подсистемы НВФ) |
| `system` | `"нвф"` \| `"сфтк"` \| `null` | нет | назначение; `null` = не решено (площади считаются одинаково) |
| `units` | `"mm"` \| `"m"` | нет | единицы координат, дефолт `"mm"` (как DWG) |
| `outer` | Poly | да | внешний контур зоны в плоскости фасада (X — горизонталь, Y — вертикаль/высота) |
| `openings[]` | список | нет | вычеты из зоны |
| `openings[].id` | строка | да | идентификатор проёма |
| `openings[].kind` | строка | да | `window` / `door` / `no_facade` (участок без фасада: витраж, ворота, соседний конструктив) / произвольное |
| `openings[].poly` | Poly | да | контур проёма |
| `source` | объект | нет | происхождение: `method` = `manual` / `dwg_auto` / `pdf_cross`; файл/слой/автор/дата |
| `meta` | объект | нет | свободные данные (не интерпретируются движком) |

## Poly

`pts` — вершины `[x, y]`, контур ЗАМКНУТЫЙ неявно (последняя соединяется
с первой; дублировать первую точку в конце можно — движок нормализует).
`bulges` — опционально, длина = длине `pts`; `bulges[i]` — выпуклость
сегмента `pts[i] → pts[i+1]` (последний — замыкающего сегмента),
как в LWPOLYLINE DXF: `b = tan(θ/4)` центрального угла дуги, `0` = прямая.
Дуги нужны для арочных проёмов и криволинейных участков; человек обводит
полилинией — дуги не теряем.

⚠ Знаковая конвенция bulge (в какую сторону физически выпукла дуга при
`b > 0`) закреплена в движке самосогласованной парой «аналитика ↔
полигонизация» и юнитами; абсолютную сторону СВЕРИТЬ по первому живому DXF
с дугой (урок Visibility1: конвенции проверяем по сырому файлу, не по
здравому смыслу). До сверки на прямоугольной геометрии (bulge=0) вопрос
не влияет.

## Правила валидации (движок)

- ≥3 вершин, ненулевая площадь; подряд идущие дубли вершин чистятся (warning).
- Контур неявно замкнутый: явный дубль первой точки в конце снимается молча;
  хвост в ≤ 0.5 мм от начала (недоведённая обводка) сливается с первой вершиной
  (warning W_AUTOCLOSED). Проверка «полилиния действительно замкнута» — на
  источнике: C#-команда до записи JSON проверяет Closed/зазор, движок больший
  зазор от штатного замыкающего сегмента отличить не может.
- Самопересечения внешнего контура — ошибка; касание — warning.
- Ориентация нормализуется: outer и openings приводятся к CCW, знак площади всегда +.
- Проём: целиком внутри outer, касание границы РАЗРЕШЕНО (дверь до низа зоны —
  штатный случай); выход за контур — ошибка.
- Проёмы попарно не пересекаются и не вложены; касание разрешено.

## Отчёт (`facade_zone_report/1`)

Выход `zone_report()`: `area_outer_m2`, `openings_total_m2`, `area_net_m2`
(нетто = брутто − Σ проёмов), `perimeter_outer_m`, по каждому проёму
`area_m2`/`perimeter_m`, `openings_perimeter_total_m` (первое приближение
погонажа откосов/противопожарных отсечек — точные правила даст Герман:
например, у двери в уровне земли откос трёхсторонний), `warnings`.
Единицы отчёта — м²/м независимо от `units`.
