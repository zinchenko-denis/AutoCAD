# Facades — состояние и хэндофф (ЧИТАТЬ ПЕРВЫМ)

> **Это проект Facades — автоматизация проектирования фасадов: навесных
> вентилируемых (НВФ) и штукатурных (СФТК). Сосед ATableSpec и ABlockGen в
> монорепо `zinchenko-denis/AutoCAD`. НЕ путать с LD/физикой.** Грабли
> среды/сборки/push — в `ATableSpec/docs/NEXT.md` (обязательны к прочтению,
> здесь не дублируются). Методика «живых эталонов» и разбора фидбэка — в
> `ABlockGen/docs/NEXT.md`. Ветка общая: `feat/auto-reactor`; `main` — только
> по явному «Пушим». Главный проектировщик направления — **Герман**
> (и НВФ, и СФТК); фидбэк разбираем по правилам ABlockGen.

## TL;DR
- **Что:** зоны фасадов (контуры + площади) → раскладка облицовки НВФ →
  подсистема НВФ; параллельно СФТК (укрываемые площади + расход материалов).
- **Порядок ценности (решение Дениса):** зоны+площади (главная боль обоих
  направлений и почти вся СФТК) → раскладка 600×600 → подсистема НВФ.
- **Этап 1 — ручное задание зоны, это НЕ запасной план:** человек обводит
  контур и проёмы полилиниями (или указывает слой) → программа валидирует,
  вычитает проёмы, считает площади/периметры, пишет зону в стандартный формат.
  Автораспознавание DWG и PDF-кросс-чек наращиваем ПОВЕРХ, итерациями с
  живыми эталонами (как ABlockGen: «укажи образцы» → дообучение на реальных
  чертежах). PDF-реализм: векторный — извлекаемая геометрия (подложка,
  кросс-чек площадей); скан — не обещаем; семантика из PDF движком —
  исследование, не обязательство.
- **Спецификации заново НЕ пишем:** фасадные блоки (кронштейны, направляющие,
  отсечки, элементы облицовки) проектируем с атрибутным контрактом, который
  уже читает ATableSpec → ведомости существующим модулем (паттерн ABlockGen).
- **Раскладка — детерминированный алгоритм, не ML:** якоря, шов, правила
  подрезки, зоны запрета; варианты — перебором правил Германа, выбор — за
  человеком. Согласованные Германом раскладки = живые эталоны в тестах.
- **Статус (18.07e, старт направления):** формат зоны `facade_zone/1`
  (docs/ZONE_FORMAT.md) + движок `engine/facade_zones.py` (валидация,
  вычеты, площади/периметры, bulge-дуги, CLI validate/report) +
  **35 юнитов зелёные**. Материалов Германа ещё нет. C#-команды нет
  (появится по паттерну ABlockGen, когда подтвердим формат на живых
  чертежах). Push 18.07e прошёл (токен получен в той же сессии);
  atspec-testdata склонирован, `dxf/facades/` ещё пуст.

## Видение (со слов Дениса, 18.07)
**Блок A — зоны (общий фундамент).** Контуры зон будущего фасада: периметры
захваток/стен с вычетами окон и нефасадных участков, из DWG/DXF; PDF — второй
независимый источник для кросс-проверки (семантика: где стена, где балкон).
Входные АР-файлы сырые, без стандарта, полны примитивов и мусора — задача
сложная, фолбэк (ручная обводка) = этап 1, см. TL;DR.
**Блок B — НВФ.** (1) Раскладка облицовки по готовому контуру: старт —
керамогранит 600×600, шов 6/8/10 мм по подсистеме; типовые алгоритмы даст
Герман (привязки к углам/окнам/контрольным точкам, где без подрезки,
минимальная ширина подрезки, симметрия); программа генерирует варианты сетки,
человек выбирает; дальше — другие форматы (1200×600 и крупнее),
параметрический элемент. (2) Подсистема по согласованной раскладке:
кронштейны несущие/опорные по альбомам техрешений (Герман загрузит),
противопожарные отсечки по периметрам окон/откосов, направляющие;
спецификации крепежа по узлам и техкартам. Типы: межэтажная (крепление в
перекрытия) и с шагом по стене (легче кронштейны/направляющие) — по несущей
способности основания.
**Блок C — СФТК.** Проще и типовее: укрываемые площади из тех же зон + расход
по коэффициентам (утеплитель по толщинам, клей, дюбели, сетка, ровнитель,
краска, уголки, примыкания). Вариативность: цвет/толщина утеплителя/система.

## Архитектура
Та же гибридная, что у соседей (проверена боем): тонкий C#-плагин (net48,
AutoCAD.NET 24.0.0, JavaScriptSerializer) + замороженный py-движок
(PyInstaller, ТОЛЬКО stdlib — ezdxf в движок не тащить, в тестах можно) +
JSON через временные файлы. Пока направление живёт движком без C# и бандла —
C#-команда обводки/чтения слоя появится после подтверждения формата на живых
чертежах Германа.

## Файлы
- `engine/facade_zones.py` — движок зон: парс `facade_zone/1`, нормализация
  (CCW, дубли, автозамыкание хвоста ≤0.5 мм), валидация (самопересечения,
  проём вне зоны, пересечение/вложенность проёмов; касания разрешены),
  площади/периметры с дугами (bulge как LWPOLYLINE), кромки проёмов
  (bottom=отлив / top+sides=откос / on_boundary=порог на границе зоны),
  группировка плоского списка контуров по вложенности
  (`build_zones_from_contours`), отчёт `facade_zone_report/1` в м²/м,
  CLI `validate|report`.
- `engine/facades_engine.py` — единый CLI движка для C# (паттерн
  vitrage_engine: `facades_engine.exe in.json out.json`), op=`zones`.
- `engine/test_facade_zones.py`, `engine/test_facades_engine.py` — 48
  юнитов (`PYTHONUTF8=1 python3 -m unittest`).
- `src/AFacadesPlugin/` — C#-плагин: `ZoneCommand.cs` (ATFZONE),
  `ZoneForm.cs` (диалог), `Plugin.cs` (BuildStamp). Бандл:
  `bundle/AFacades.bundle/PackageContents.xml`; CI: build.yml/check.yml
  дополнены (AFacades.bundle.zip в latest, компиляция+юниты на ветках).
- `docs/ZONE_FORMAT.md` — контракт формата зоны (вход движка, выход будущей
  C#-обводки и автораспознавания).
- `examples/zone_example.json` — референс-пример (12×3 м, два окна + дверь;
  нетто 29.610 м²).
- Эталоны, когда появятся: `atspec-testdata/dxf/facades/` (чертежи Германа +
  его ручные результаты; пуш в main testdata можно сразу).

## Решения 18.07e (технические, пересматриваемые)
- **Одна папка `Facades/`**, не две (НВФ/СФТК отдельно, как диктовал Денис):
  общий блок зон один, направления разойдутся модулями `nvf_layout.py` /
  `sftk_calc.py` внутри. Денис может переименовать/разделить позже.
- **Формат зоны** — JSON `facade_zone/1`, координаты в плоскости фасада
  (X — горизонталь, Y — высота), мм; неявно замкнутые полилинии с bulge
  (человек обводит полилинией — дуги арочных проёмов не теряем).
- **Bulge-конвенция:** аналитика (площадь сегмента, длина дуги) и
  полигонизация самосогласованы и закреплены юнитами; внутренняя конвенция —
  «b>0 = вершина дуги справа от направления хорды». ⚠ Абсолютную сторону
  СВЕРИТЬ с живым DXF при первом реальном арочном проёме (урок Visibility1:
  конвенцию проверяем по сырому файлу, не по здравому смыслу). Если
  окажется зеркальной — флип знака в одном месте (`_arc_params`: h и delta,
  `_arc_segment_area`: знак вклада).
- **Допуски:** GEO_TOL=0.5 мм (замыкание/касания/глубина «настоящего»
  пересечения — в духе допуска осей ABlockGen), CHORD_TOL=0.5 мм
  (полигонизация дуг), TINY_OPENING=0.01 м² (warning на мусор обводки).
- **Касания законны:** дверь до низа зоны, окна встык, проём краем на
  границе — валидно; ошибками считаются только «настоящие» (глубже 0.5 мм)
  пересечения/выходы/вложенность. Скользящее перекрытие прямоугольников
  одинаковой высоты вершинными тестами не ловится — добавлены пробы середин
  рёбер (`_probe_points`).
- **Погонаж откосов** в отчёте = сумма периметров проёмов, первое
  приближение для отсечек/примыканий; точные правила (дверь в уровне земли —
  трёхсторонний откос и т.п.) — от Германа.
- **Метки заходов** — сквозные по дню через все модули репо (18.07b/c/d были
  у ABlockGen → этот заход 18.07e).

2. **build-trigger пушит только сессия, получившая «Собираем» от Дениса
   в СВОЁМ чате, и только от СВЕЖЕГО origin/feat/auto-reactor** (build.yml
   собирает все три бандла с ветки — чужая работа соберётся заодно, это
   норм). Одна сборка за раз; чужой недособранный build-trigger не
   перетирать: увидел свежий чужой пуш build-trigger (<15 мин) — подожди.
3. Общие файлы (NEXT.md, AFacadesPlugin/*, бандл, CI) — конфликты решает
   пушущий ребейзом; статусы заходов только ДОПИСЫВАЮТСЯ сверху.
4. Метки заходов сквозные по дню через обе сессии.

## Стык «зоны → раскладка» (ответ на В3 CLADDING.md — от сессии зон)

**«Метки, сделанные ранее» из сценария Германа = ЗОНЫ ATFZONE.** Это его
же ТЗ этапа 1: «создаёт атрибут с целью маркировки данных контуров» —
маркировка зон и есть метки. Зона уже несёт всё, что нужно раскладке:
- контуры (outer+openings) в слое облицовки; штриховка АССОЦИАТИВНА —
  ObjectId контуров достаются из неё (GetAssociatedObjectIds), либо
  полная геометрия из `<dwg>_fzones.json` (facade_zone/1: pts+bulges);
- Xrecord «ATFZONE» на штриховке И марке: {zone_id, cladding, report}
  (чтение — `ZoneCommand.ReadZoneData`, JSON чанками по 250);
- cladding зоны = вид облицовки (п.1 сценария) — можно предзаполнять.
ПРЕДЛОЖЕНИЕ сессии раскладки: ATCLAD принимает выбор штриховок/марок
ATFZONE как «метки» (без повторной обводки), а СВОИ параметры раскладки
(tile/датум/русты/режим) пишет ДОПОЛНИТЕЛЬНЫМ ключом «ATCLAD» в тот же
extension dictionary штриховки зоны (паттерн StoreZoneData готов к
переиспользованию) — тогда «выбрать метки» на перегенерацию покрывает и
зоны, и параметры. Отдельная XData-метка на голом контуре нужна только
для раскладки БЕЗ зоны (если Герман так работает — уточнить).

Ответ на В6 (от сессии зон, по KB): да — вертикальный руст = шов между
камнями в ряду, горизонтальный = между рядами; в боевых проектах швы
5±2 мм (Standart/КАФТ, 245/22-1) и 8±2 мм (Вектор, Бугры-2018), обычно
в=г; раздельные в/г русты в модели — правильно.
