# Предметная и архитектурная ревизия, 30.09.2026

Срез: AutoCAD e2a4e4d; приватные первоисточники atspec-testdata 18a80ca. Сопоставлены ТЗ, журналы, прошлое ревью/ответ, АТР и расчётная методика. Это техническая проверка реализации и её согласованности с переданными источниками. Нормативную актуальность перечисленных в старой KB документов не подтверждаю и не использую старые конспекты как действующую норму. Производственные файлы не изменялись. По поручению основного ревизора добавлены только воспроизведения в tools/review_3009.

## Новые подтверждённые дефекты

### D1 / P1. Смена каркаса меняет явно заданную массу облицовки 25 → 8 кг/м²

Файл `AFrame/src/AFramePlugin/FrameSettings.cs:208-218`. Метод `SetSubType("interfloor")` определяет «значение не трогали» лишь по равенству числу 25, не по происхождению ввода. Поле Cladding при этом остаётся прежним. Таким образом, КГ, клинкер, бетон или композит с явно заданной массой 25 превращаются в материал массой 8. `CalcDict` передаёт это значение движку (`:155-162`), проверка `Validate` его принимает. В форме изменение видно в поле массы, но предупреждения о смене исходных данных нет.

Это не предположение по C#: настоящий FrameSettings собран mcs и выполнен mono вместе с `tools/review_3009/FrameSettingsProbe.cs`. Все четыре материала дали 25 → 8, validation=accepted; exit 1. Существующий `AFrame/tools/frame_ui/UiCheck.cs:47-51` считает это поведение правильным, поскольку закрепляет старое значение из прежнего пресета металлокассет.

Влияние движка: прямоугольник 6000×6000, оси 600 мм, перекрытия 0/3000/6000, керамогранит, II/B/30 м, вынос 230, анкер 3000 Н. После смены типа при q=8 шаги 450/200; с сохранёнными q=25 — 350/200. Это отдельный эффект от D2; оба расчёта здесь используют один и тот же текущий gamma=1.05. Evidence `weight_switch_repro.json`.

Исправление: масса — атрибут выбранной облицовки и пользовательского ввода, смена схемы каркаса её не меняет. Если нужны рекомендации массы, применять их только при явном выборе материала и показывать источник/подтверждение. Не распознавать «дефолт» сравнением с магическим числом.

### D2 / P1. Коэффициент веса зависит от каркаса, а не материала

`AFrame/engine/systems.json:61-69` фиксирует для межэтажной gamma_clad=1.05; вертикальная и ортогональная имеют 1.1. `FrameSettings.CalcDict` не передаёт поправку по материалу. `_apply_calc` берёт число из пресета (`AFrame/engine/frame_plan.py:817-835`). Выбранный пользователем материал остаётся отдельным полем запроса, не влияет на этот коэффициент.

Их же методика `atspec-testdata/docs/facades_calc/METHOD_CALC.md`, §1, задаёт для КГ/ФЦП/клинкера 1.1, АКП 1.2, металлокассет 1.05. Проверен непосредственно первичный PDF `Static_VEKTOR5_tip4_Regenbogen_AKP_28m.pdf`, стр.3: АКП, масса7.2, gamma1.2; `Static_VEKTOR4_tip1_Regenbogen_klinker_28m.pdf`, стр.3: клинкер, gamma1.1. Это замечание о несогласованности с заявленной исходной методикой, без вывода, что указанные коэффициенты автоматически нормативно достаточны для любого проекта.

Прогоны одинаковой геометрии 6000×6000, осей600, перекрытий0/3000/6000:

| Материал/вход | Текущий фактор → шаг ряд/угол | Фактор исходной методики → шаг |
|---|---|---|
| КГ25; II/B/30м; e230; Na2820 | 1.05 → 350/200 | 1.1 → 300/200 |
| Клинкер45; II/B/30м; e230; Na3500 | 1.05 → 350/200 | 1.1 → 300/200 |
| АКП7.2; II/A/28м; e400; Na3040 | 1.05 → 350/200 | 1.2 → 300/200 |

Все значения получены frame_plan. Evidence `gamma_interfloor_porcelain.json`, `gamma_interfloor_clinker.json`, `gamma_interfloor_composite.json`; три негативных регрессионных теста `test_domain_review.py`. Подставлять недостающий коэффициент по названию каркаса опасно; нужен самостоятельный материал/расчётный набор с видимым фактором и источником.

### D3 / P1 по предметной пригодности. «Композит» молча выдаёт кляммеры керамогранита

`AFrame/engine/frame_plan.py:1183-1201` различает плитку и прочее; composite и porcelain проходят одну ветвь. В форме режимы all/frame/clamps для композита доступны (`AFrame/src/AFramePlugin/FrameForm.cs:283-287`); отсутствует выбор способа крепления АКП. Прогон стены6000×6000, оси/ряды600 дал в обоих случаях 121 полностью идентичный кляммер. Ошибки/замечания о способе крепления нет. Evidence `composite_repro.json`; четвёртый тест `test_domain_review.py`.

АТР Вектор-5 2017, стр.135 (лист11.1), описывает 8 способов АКП: салазки, икли, пластины, усилители либо заклёпки; конспект `Facades/docs/kb/atr_vector5_2017.md:18-28`. Кляммеры КГ не могут служить автоматической спецификацией этого узла. Комментарий в коде ссылается на пожелание сохранить прежний алгоритм, но такое пожелание не выбирает и не подтверждает крепление АКП.

Минимальный безопасный продуктовый вариант: для композита разрешить расчёт/геометрию каркаса при явно согласованном наборе компонентов, режимы креплений пометить как неподдержанные; затем реализовать выбранную систему крепления, а не подменять её кляммерами КГ. Это не требование немедленно автоматизировать все восемь вариантов.

## Типы 1–5: что действительно покрыто

Не следует путать «Вектор-1/4/5» (семейство по облицовке) с «типом1–5» внутри АТР (схема подконструкции). Код использует три пользовательские схемы и отдельный справочник, поэтому совпадение цифр не означает покрытие.

| Тип в АТР Вектор-1 2015 | Пользовательская схема ATFRAME | Статус |
|---|---|---|
| 1, вертикальная Г/Т/НГ, стр.18 | vertical | Рабочее геометрическое ядро, ограниченный набор сечений и узлов по ТЗ Германа; не все варианты АТР |
| 2, вертикальная С/Омега + П-кронштейн, стр.29 | Отдельного выбора нет | Отдельная схема с компонентной совместимостью не реализована; наличие ШП в vertical не доказывает покрытие типа2 |
| 3, ортогональная неусиленная, стр.39 | ortho | Рабочее ядро горизонтальныеГП+вертикальныеШП/Z, частные правила ТЗ; расчёт каждого выданного компонента не обеспечен |
| 4, ортогональная усиленная НГП+НСП/НШП, стр.52 | interfloor | Главный межэтажный путь, НСП у откосов добавлены build30; остаются конкретные расчётно-геометрические дефекты из отчёта frame_audit |
| 5, вертикальная усиленная, стр.61 | Отдельного выбора нет | В frame_calc есть interfloor_direct, но интерфейс/геометрия генерируют interfloor с горизонтальнымиНГП и удлинителем; полноценного end-to-end типа5 нет |

Источник матрицы типов `Facades/docs/kb/atr_vector1_2015.md:9-18`; перечень UI `FrameSettings.cs:53`; calc `frame_calc.py:148-149`. Первичная стр.52 АТР визуально проверена: НГП, НСП, вставки, направляющие у обоих боковых откосов видны. Исправление build30 отвечает этой принципиальной топологии; картинка альбома сама по себе не подтверждает каждый числовой отступ100/150 мм нового алгоритма. Их происхождение должно оставаться отдельным: ТЗ/решение инженера/расчёт.

NordFOX — источник для будущей архитектуры, не реализованный производитель: в systems.json нет пресета NordFOX, его фиксированные/подвижные опоры и классы длины по конспекту не покрываются добавлением чисел в существующий Vector-пресет.

## Граница расчётной применимости

Плюс: воспроизводимый детерминированный движок, расчёт до раскладки, эталоны по реальным расчётам, улучшенная грузовая ширина после предыдущего ревью. Исправленные проблемы прошлой рецензии не повторяю как новые.

Однако `frame_calc` — реализация конкретной восстановленной методики, а не полный проверяющий модуль для любого объекта НВФ. Это важно отделить от дефектов D1/D2 и от повторяемости арифметики:

- Справочник содержит ограниченные сечения/кронштейны, постоянные E/Ry и заклёпочные параметры (`frame_calc.py:41-50,77-110`). Их применимость к выбранным на чертеже произвольным образцам не проверяется. Прочность образца блока не определяется его геометрическим размером или именем.
- НГП хранится без Wx/Jx/A; расчёт проверяет один profile, а не все элементы готовой цепочки (`frame_calc.py:102,231-251`). Кляммер, шина плитки, её крепление, анкерный срез/сочетание, противопожарный узел не появляются в checks. Это описание покрытия кода, не вывод о нормативном нарушении.
- Лёд использует фиксированный ICE_K=1.6 и дефолт районаII (`frame_calc.py:61,178`), угловые коэффициенты фиксированы1.2/2.2; UI допускает 1–500м (`FrameSettings.cs:243`) без подтверждения конкретной аэродинамики/каталожной области. Для широкого применения нужен паспорт допустимых входов и источник каждой константы.
- Независимый расчёт по окончательной геометрии отсутствует. Ревизия AFrame воспроизвела медиану этажей вместо фактического длинного пролёта. Соответствие марки НСП рассчитанному сечению требует отдельного подтверждения: самостоятельный доказанный отказ по этому наблюдению не заявляется.
- Даже `calc_report.inputs` не содержит полного набора gamma, bracket/extender, rivets, ice, версии методики (`frame_plan.py:922-927`). Сейчас нельзя считать его самостоятельным расчётным документом, пригодным для последующей проверки без кода/пресета.

В приватном AUDIT_VECTOR_CALC.md есть прежние гипотезы о более строгой проверке. Не копировать их нормативные заключения без проверки: документ сам предупреждает, что ссылки даны по памяти. Сомнительные физические допущения нужно отдельно согласовать с инженером и системодержателем на фактическом узле; произвольно «ужесточить» коэффициенты и назвать это сертификацией было бы неправильно.

## До комплекта производителя: полезное ядро, но комплект ещё не полный

Эталон собственной базы `Facades/docs/kb/projects_rules.md:10-29`: общие данные, парные раскладки облицовки/каркаса, узлы, схемы утепления/обрамлений/крепления, спецификация, ВР, прочностной расчёт/ПЗ. Сейчас автоматизированы значимые части геометрии и ведомостей; нет единого механизма выпуска и проверки целого комплекта.

Конкретные границы:

1. Вставка межэтажной — один условный fitting, а в источнике пара ВС-300+В-70. Код `frame_plan.py:1496-1506`; давно открытый пункт `AFrame/docs/NEXT.md:115-118`. Не новая авария, но готовой спецификацией метизов выход не является.
2. Угловые спецузлы, деформационные швы с узловой номенклатурой, противопожарные короба/полосы дополнительного крепления, крепёж, изоляция и примыкания должны иметь выбранные типы/источники и выпускные количества. Наличие погонажа откоса в ATFTABLE не означает, что узел полностью спроектирован и специфицирован.
3. Фигурные подрезки у ската пока полилинии и выпадают из блоковой спецификации; это честно зафиксировано в последнем PDF, генератор `AFrame/docs/make_build30_3009.py` (разделы4/6). До закупочной ведомости нужен принятый способ учёта этих деталей/заготовок.
4. Для клинкера/бетона источником шин сейчас служат ответы Германа. В запросе свежего АТР Вектор-4 в PDF30 есть реальная необходимость: отсутствующий альбом не следует считать заменённым АТР Вектор-1.
5. Последние PDF — хорошие инкрементальные инструкции с реальными картинками/списком приёмки, но десятки дополнений не заменяют одного актуального руководства по границам функций и решениям инженера. FRAME_TZ содержит историческую фразу о межэтажной/ортогональной как «заглушках» ниже актуальной шапки: документ легко прочесть противоречиво.

## Зрелость, экономика, следующий шаг

Профессионально это уже полезный инженерный инструмент под управлением конструктора. Нельзя назвать весь набор ни игрушкой, ни готовым автономным конструктором НВФ. ATableSpec имеет отдельно документированную боевую приёмку; зрелость AFrame/новой плиточной ветки не наследуется от него. По состоянию журнала живой приёмки build30 ещё ждут.

Экономический выигрыш следует считать по полному циклу «исходныйDWG → ручная подготовка → генерация → исправление → провереннаяСО/ВР → правка проекта», а не только времени Python. Нет замеров трудозатрат/ставок/стоимости ошибок, поэтому достоверной суммы экономии или процента готовности нет. Приоритет сейчас — убрать неверные исходные нагрузки и разрыв расчёт↔чертёж; это сокращает риск дорогостоящей переделки и даёт проверяемый пилот быстрее, чем добавление ещё одного производителя.

Рекомендуемая последовательность без переписывания боевого ядра:

1. Закрыть D1/D2 и найденные frame_audit разрывы; временно явно ограничить неподдержанные крепления композита. Прогон на текущих примерах, независимо от штатного зелёногоCI.
2. Ввести паспорт проекта/зоны: материал и его масса/коэффициент; система и тип; выбранные компоненты; основание/анкер; климат; перекрытия; источник/версия метода. Расчёт и блоки должны читать одни IDs, не дублировать словари маркировок.
3. Добавить проверку выданной схемы: реальные пролёты/опоры/нагруженные участки/профили/крепления. Выделить статус «геометрия», «расчёт поддержанных элементов», «инженерно принято», не скрывать непокрытые проверки за единым ok.
4. Сначала один полный эталонный объект Вектор выбранного типа с комплектом СО/ВР/узлов/расчёта и независимым инженерным сверением; потом расширение на следующий тип и производителя.
5. Архитектурно отделить геометрическое ядро, правила конкретной системы и выпуск документов. Дублирование малых stdlib-помощников между независимыми бандлами оправдано текущим выпуском; главная проблема — разрозненные источники правил и разрыв идентичности компонентов. Перенос всех правил в огромный общий справочник без проверки областей применимости лишь перенесёт ошибку из кода вJSON.

Полезные измерения пилота: время по этапам, число ручных исправлений на1000м², количество неподдержанных/непринятых узлов, повторный выпуск после изменения одного окна/массы/профиля, расхождение количества/погонажа с независимым комплектом. Синтетика должна включать семантические оракулы (материал не меняется при смене каркаса, каждый нарисованный профиль равен рассчитанному), а не только повторять текущие defaults.
