# Независимый аудит AClad — 30.09.2026

Срез: AutoCAD HEAD e2a4e4d, продуктовый код не менялся. Анализировались CLAUDE.md, CHRONOLOGY.md, текущий AClad NEXT.md, CLADDING.md, TILE_PATTERN.md, прежние REVIEW/RESPONSE и Python/C# исходники. Произвольные DLL/AutoCAD API здесь не запускались. Логи — рядом с этим отчётом; тесты — tools/review_3009/test_clad_frontons.py. Чертежи всех новых тестов синтетические.

## Вердикт

Регрессии штатных тестов нет, эталон 290×82 воспроизводится точно; ускорение Python не опровергнуто. Однако новая поддержка фронтонов недостаточно проверена: найдено закрытие проёма, потеря покрытия у вогнутой линии крыши и отказ треугольного фронтона. Кроме того, прежний A2 по ATCLAD нельзя считать закрытым: отвергнутая зона продолжает попадать в список успешных, по которому C# удаляет прежнюю геометрию.

## Пять доказанных находок

### CL-1, P1: ATCLAD — частичный успех всё ещё разрешает удаление прежней раскладки отказавшей зоны

Статус: не новая идея, **неполностью устранённый A2** из docs/REVIEW_RESPONSE_24.09.md:54.

В AClad/engine/clad_engine.py:300–306 каждая зона безусловно добавляется в per_zone, даже если cladding_plan вернул ok=true с нулём вставок и примечанием «пропуск». В AClad/src/ACladPlugin/CladCommand.cs:978–990 все per_zone превращаются в okOwners без проверки статуса; строки 462, 476–477 передают их в удаление. AClad/src/ACladPlugin/TilePatternCommand.cs:1498–1506 стирает handles владельцев из ok.

Воспроизведение: один нормальный контур 2400×2400, второй — с отклонением ребра на 10 мм при допуске 5 мм. CLI возвращает GOOD=16 вставок, BAD=0, BAD присутствует в per_zone и отмечен только текстом «пропуск». Если до правки контура BAD имел раскладку, при совместном запуске с GOOD C# считает BAD успешным и допускает удаление его прежних объектов. Отдельный запуск только BAD защищён общей проверкой пустого inserts; смешанный выбор — нет.

Доказательство: Python-контракт воспроизведён автоматически тестом test_atclad_rejected_zone_not_listed_as_success; путь удаления установлен по C# исходникам. **Фактическое удаление в AutoCAD не исполнялось.**

Правка: явный статус success/skipped/error для каждой зоны; okOwners только по успешным. Не использовать просто tiles>0 без решения смысла законного пустого результата. Для зон с несколькими частями также проверять успешность всех частей владельца до удаления общего списка handles.

### CL-2, P1: ATTILE после обрезки по скату полностью закрывает маленький проём

Статус: новое, связано с добавлением фронтонов 29.09.

AClad/engine/tile_pattern.py:1298–1299 берёт только rings[0], внутренние кольца игнорирует; строки 1328–1329 заменяют результат одним кольцом. Окно, целиком лежащее внутри одной плитки у ската, теряется.

Синтетика: фасад 6000×3000 мм, конёк(3000,4500), плитка 1200×1200 мм, шов 10 мм, режимshaped=keep, окно[5000,2600]–[5300,2900]. Движок ok=true; Shapely измеряет **90 000 мм² =0,09 м² перекрытия окна**, то есть всё окно 300×300. Окончательный многоугольник имеет одно наружное кольцо и внутреннего проёма не содержит. Тест test_attile_keeps_enclosed_opening_after_slope_clip падает.

Иллюстрация: docs/review_3009/gable_opening.png, генератор — тот же тест с --render. Визуально проверена. Это изображение результата движка, не снимок AutoCAD.

Правка: клиппинг должен сохранять топологию отверстий и несколько результирующих компонент; либо после ската заново вычитать проёмы. Раскрой, площадь и small/tiny пересчитать по итоговой геометрии.

### CL-3, P1/P2: ATTILE и ATCLAD теряют покрытие у вогнутого соединения двух фронтонов

Статус: новое, расширение формы не ограничено в интерфейсе или движке; неподдержанная форма принимается как успешная.

AClad/engine/tile_pattern.py:1305–1313 и AClad/engine/cladding_plan.py:622–631 режут плитку последовательным пересечением с полуплоскостями всех скатов, bbox которых пересекает кусок. На вогнутом соединении это не равно пересечению с фасадом.

Контур: [(0,0),(6000,0),(6000,3000),(4500,4500),(3000,3000),(1500,4500),(0,3000)]. При плитке 1200×1200, швах 0 и min_piece=0 оба движка возвращают 19 кусков. Площадь фасада 22,5 м², объединение кусков 21,78 м²: **потеря 0,72 м²**, наружного выхода 0. Это не поглощённые тонкие полоски. Тесты test_attile_concave_roof_preserves_coverage и test_atclad_concave_roof_preserves_coverage падают. Дополнительная независимая сетка с обычным швом 10 мм также дала потерю 720000 мм² (ожидаемая площадь плитки 22190250, фактическая 21470250).

Правка: корректное пересечение с невыпуклым полигоном (при stdlib — разбиение на поддерживаемые компоненты) либо явный отказ для неподдержанных соединений до изменения чертежа. Поддержка только одного выпуклого фронтона должна проверяться кодом, а не предполагаться.

### CL-4, P2: ATCLAD не раскладывает отдельный треугольный фронтон

Статус: неполнота новой функции 30.09; прежнее ограничение ортогонального контура осталось перед новым обработчиком.

AClad/engine/cladding_plan.py:462–464 требует минимум 4 вершины и возвращает «меньше 4 вершин — пропуск» ещё до разбора скатов. Контур[(0,0),(6000,0),(3000,1500)] геометрически корректен, C# принимает замкнутую полилинию с 3 вершинами, ATTILE её раскладывает. ATCLAD возвращает ok=true и 0 вставок. Тест test_atclad_accepts_triangular_fronton падает.

Правка: минимум 3 вершины, с отдельной проверкой ненулевой площади/валидности; при отказе вернуть понятный статус, не «успех».

### CL-5, P2: большие абсолютные координаты меняют состав раскладки фронтона

Статус: новый воспроизведённый сценарий; формула signed_area старше фронтонов, новая обрезка использует её для удаления/классификации кусков.

AClad/engine/tile_pattern.py:122–129 считает площадь разностью произведений абсолютных координат; строки 1314–1317 применяют результат для удаления/сравнения площади. В AClad/engine/cladding_plan.py:632–636 тот же риск. Утрата значащих разрядов не устраняется единым EPS 1e-6.

Тест ATTILE: тот же фронтон 6000×4500, плитка 290×82, швы 7. У начала координат 901 кусок; при переносе всех вершин на X=Y=4 000 000 000 мм —899 кусков. При 1e10 —889, при 1e11 —726. Само перенесение не должно менять раскладку. Test test_attile_large_coordinate_translation_preserves_pieces проверяет 4e9. Это край больших геопривязанных координат, не ошибка обычного фасада в локальной системе.

Правка: площадь относительно локального начала контура, math.fsum при необходимости; переносная инвариантность в тестах. Аналогичную абсолютную формулу в clad_engine._group_contours:176–178 тоже привести к локальному началу.

## Что уже известно и не выдаётся за новое

1. Динблок с базой в центре/растяжкой в обе стороны: OffX/OffY от исходного образца применяется до изменения размеров (TilePatternCommand.cs:1036–1046). Смещение подрезки известно с NEXT 23.09m и сознательно не включено в 26.09. Код по-прежнему без компенсации итогового габарита. Живой тест нужен.
2. TrySetNum (CladCommand.cs:1118–1124) проверяет старое значение, затем возвращает true после setter без обратного чтения; dynFail лишь предупреждает, вставка с неверным размером остаётся. Уже признанный открытый пункт 24.09 и 23.09m.
3. EnsureTileBlock возвращает существующее определение по имени без проверки размеров; известный отложенный пункт. Новых измеренных коллизий имён в этом заходе нет.
4. COPY защищён owner, мягкими ссылками 330 и XlateReferences; нынешний код новее формулировки RESPONSE 24.09. Проверка label_refs_check проходит. Реальное перемаппирование COPY / DeepCloneObjects, Undo и частично скопированных групп без AutoCAD не подтверждено.
5. Фигурные куски ATCLAD — полилинии, не входят в спецификацию блоков. Это явно заявленное и вынесенное на согласование ограничение сборки 30, не новая находка.
6. Культура чисел: в BondSettings.TryParseNum нормализация запятой и invariant parsing, в форматировании/динамических свойствах invariant culture. Исполнение pure-settings/contract выполняет основной ревизор; я не приписываю себе этот прогон.
