Роли выполняют настоящий движок и `FrameSettings`, но не действия пользователя в интерфейсе AutoCAD. В полной синтетике сохранены точные безопасные отказы неподтверждённых расчётных схем; они не скрываются как успешные расчёты.

Сначала были воспроизведены ложные подтверждения марки: семейство «ГП» вместо полной марки, а также слияние `1,2` с `12` и `4-040` с `40-40`. Итоговый guard требует совпадения полной марки с сохранёнными числовыми разделителями. Он повторно читает текущее состояние, кеширует только допустимое соответствие определения и марки, не вызывает setters. Реальные динамические блоки дополнительно проверяются в живом пилоте.

## Воспроизведение

Из корня репозитория, с Python 3.12, shapely/openpyxl/ezdxf и Mono/mcs:

```bash
python tools/atr_review_3009/run_checks.py --out /tmp/q05-gates
python tools/fixes_3009/compile_facades.py --references /path/to/extracted/nuget-packages --out /tmp/q05-compile
python Facades/tools/zones_synth.py
python AClad/tools/attile_synth.py
python AFrame/tools/frame_synth.py --seed 2909
python tools/roles_synth.py --seed 2909
```

Для каркаса и ролей повторить seed `77` и `5`. Полные версии зависимостей и SHA NuGet/Mono-пакетов — в `environment/`. При наличии .NET SDK компиляция плагинов использует существующие проекты без `--references`. Windows CI выполняет чистые probes как net48 и отдельно компилирует Store doubles; команды закреплены в `.github/workflows/check.yml`.

Адресные проверки и их зависимости описаны в [tools/frame_quantities_3009/README.md](../../tools/frame_quantities_3009/README.md). Отсутствующие компиляторы или references дают отказ, а не успешный пропуск.

## Производительность

Измеряются три разных этапа:

1. `performance/engine/`: Python-движок, ручная и ограниченная расчётная цепочка при целевых 10k/50k/150k элементов. Фактический размер округлён до целого числа зон и указан в манифесте.
2. `performance/core/`: чистая C# агрегация 10k/50k/150k, полная и частичная область. Проверяются все исходные элементы и связи, при уникальных ID не создаются канонические строки сравнения. На 150k проверены 150k элементов и 300k связей в обоих проходах выбора.
3. `performance/store_current/` и `performance/store_baseline_6222041/`: настоящий адаптер с инструментированными CAD doubles. Отдельно записаны Store/Read, подготовительный старый LayoutStore, счётчики CAD-вызовов, память и наблюдаемое время. Полный новый прогон содержит 12 случаев: облицовка/каркас × 10/50/100 зон по 300 деталей и по одной зоне с 10k/50k/150k деталей.

```bash
python tools/frame_quantities_3009/test_frame_engine_perf.py --out /tmp/q05-engine-perf
python tools/frame_quantities_3009/test_frame_core_perf.py --out /tmp/q05-core-perf
python tools/quantities_3009/test_quantity_store_perf.py --large --out /tmp/q05-store-perf
```

`performance/store_all_selected/` дополнительно содержит два фактических чтения с выделением всех 150 000 физических деталей: облицовка и каркас. Оба результата совпали по отпечатку с чтением через владельца, вернули 150 000 элементов и выполнили один обход ModelSpace (150 004 посещения в этой фикстуре). Исходник отдельного измерительного probe и его SHA сохранены рядом. Это дополнительная локальная проверка; число обязательных групп остаётся 35.

В CI Store ограничен четырьмя короткими случаями 10/40 зон по 3 детали. Порогов в секундах нет: проверяется ограниченный рост обращений к объектам, уникальной геометрии зон и один обход ModelSpace. Старый `LayoutGeometryGuard.Store` имеет отдельный технический долг повторных снимков источников; его подготовительная запись не включена в новую гарантию для Store/Read ведомости.

Для baseline сохранены исходная ревизия/SHA, синтетические fixtures, точная инструментализация doubles и самостоятельный C# runner. Продуктовые файлы извлечены из `6222041` без изменений; у тестового `QuantityStoreCheck` для runner только `Fixtures` и `Fixture` сделаны публичными. Подробности — `performance/store_baseline_6222041/ARCHITECTURE_AND_BASELINE.md`.

`performance/core_comparison_diagnostic/` — отдельное наблюдательное сравнение ядра облицовки до/после оптимизации: 150k элементов, 8 итоговых строк, 6,966 → 1,623 секунды. Это не финальный gate всех файлов и не время построения DWG. Итоговое ядро подтверждено отдельным свежим `performance/core/manifest.json`. Нулевой PeakWorkingSet в старом raw-снимке означает недоступную метрику; это не нулевой расход памяти.

RSS — верхний уровень памяти всего процесса fixtures, включая предшествующие фазы, оставшиеся CAD doubles и исходный DTO построения вместе с новым Read; это не изолированная стоимость чтения; `GC.GetTotalMemory` — живая управляемая память на момент снимка. Простые полилинии doubles не моделируют стоимость реальных слоёв, динамических блоков, регенерации или сохранения DWG. Времена одиночных прогонов описывают этот стенд, а не гарантируют эксплуатационную скорость.

Живой AutoCAD, Esc/Undo/Redo, SaveAs/повторное открытие, настоящие образцы блоков и совместный откат DWG/XLSX остаются отдельной приёмкой по [FRAME_QUANTITIES_30.09.md](../FRAME_QUANTITIES_30.09.md). Полная статика, тип 5/NordFOX, неподтверждённые сечения и узел крепления АКП этими тестами не подтверждаются.
