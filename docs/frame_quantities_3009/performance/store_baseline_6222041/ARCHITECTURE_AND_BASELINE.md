# Q-05: независимый разбор производительности DWG-паспортов

Базовая версия: `6222041b38cf63b19373c6c155319b850264652f`. Продуктовые файлы извлечены из Git без изменений; счётчики добавлены только в CAD doubles. Замеры Mono отражают управляемый адаптер, не время AutoCAD. Область — запись/проверка количества, без инженерного расчёта и реального рендеринга DWG.

## История и сохранённые принципы

AClad/docs/NEXT.md, записи 26.09b/c: жалобы Германа на сверхлинейное время были связаны с пересчётом динамических блоков на каждую вставку, ассоциативными заливками, потоком сообщений и одной огромной транзакцией. Тогда введены прототипы и пакетные копии, неассоциативные заливки, пачки и запись конечных меток после успешной отрисовки. Исторические количественные оценки описывали число операций; живое время после изменений оставалось непроверенным. Эта работа не повторяет закрытые правки и не отменяет ни прототипы, ни пачки, ни откат.

## Воспроизведение

Каждая синтетическая зона содержит реальную зону Facades engine, созданную и проверенную настоящими ZoneGeometryGuard/LayoutGeometryGuard. У двух владельцев зоны (Hatch/MText) одинаковая полная группа источников. Сами исходные зоны намеренно совпадают геометрически: проверяется идентичность и стоимость проверки источников, а не пространственная корректность раскладки. Физические элементы — независимые полилинии. Снимки JSON фиксируют каждую фазу и метрики.

Фикстура использует простые полилинии и стандартный цвет, без динамических блоков и без отдельного LayerId. В настоящем DWG добавятся чтения слоя, атрибутов и определений блоков; приведённые коэффициенты CAD-вызовов относятся только к этой контролируемой фикстуре, а не к любой модели.

Peak RSS — process high-water mark `/proc/self/status`; после чтения включает ранее выполненную запись. `GC.GetTotalMemory` в JSON — объём живой managed-памяти в момент измерения, не сумма выделений. Счётчики операций детерминированы; единичные wall-time замеры ориентировочны. В doubles первое получение ModelSpace лениво создаёт два служебных объекта: это их техническая особенность, а не запись из продуктового Read.

## Корень роста

Обозначения: Z — число зон, P — число физических деталей. Для выбранной фикстуры базовые счётчики точно совпали с:

- `LayoutGeometryGuard.Store` для всех владельцев: `24 Z² + 26 Z` чтений CAD.
- `FacadeQuantityStore.Store`: `2 P + 36 Z² + 44 Z` чтений CAD.
- `ReadCladding`: `7 P + 36 Z² + 55 Z + 6` чтений CAD.
- Внутри одной записи либо чтения паспорта границы Hatch прочитаны `6 Z² + 4 Z` раз; уникальных исходных границ только `2 Z`.

В Store/VerifyEntry цикл по владельцам вызывает LayoutGeometryGuard.Verify. Verify снова обходит все источники группы; для MText дополнительно проверяет канонический Hatch. Каждый ZoneGeometryGuard.Verify заново читает Xrecord, геометрию и канонизирует JSON. Отдельно прежний LayoutGeometryGuard.Store при записи каждой метки повторно проверяет всю группу.

Независимая ось нагрузки P уже линейна по CAD-вызовам, но тяжела по памяти: при 150 000 деталях чтение заняло 1.92 GiB peak RSS в doubles. Причины в коде: сериализованный report_json внутри сериализованного Entry, распаковка через дополнительную копию byte[], полное DTO-дерево, нормализация геометрии и построение строк. Это не доказательство такого же RSS AutoCAD, но воспроизводимое ограничение реализации.

## Безопасные изменения

1. Контекст верификации только на один синхронный Store/Read: кэш уникальных проверенных зон и точных групп ссылок. Нельзя сохранять его между командами, диалогами, транзакционными изменениями или повторными чтениями.
2. Для нового frame-паспорта один снимок уникальных источников в NOD, независимые frame owner/element keys. Не применять LayoutGeometryGuard.Store к каждому владельцу ATFRAME: это повторило бы квадратную запись и затронуло ATLAYOUT_CURRENT облицовки.
3. Снимок frame должен проверять реальные контуры, исходные метки/оси и ссылки. Для Hatch нужны также Associative, HatchStyle и ассоциированные ObjectId; общий fingerprint графики сам по себе их ранее не включал.
4. Одна итоговая агрегация на Read, возврат готовых Rows и fingerprint области. Выбор всех физических объектов группировать по run, не удерживая копию полного Stamp для каждой детали.
5. Сохранять полный проход по физическим деталям и один ModelSpace scan для копий. Убирать эти проверки ради скорости нельзя; кэши через mutation также недопустимы.
6. Отдельный typed frame_report и потоковая UTF-8 обработка снижают копирование данных. Сохранить одинаковый лимит чтения/записи, точные отказы и совместимость cladding schema 1.

## Остаточный долг

Legacy LayoutGeometryGuard.Store всё ещё пишет полный набор источников на каждом владельце и заново валидирует группу; старые *_GEOMETRY содержат O(Z²) суммарных metadata bytes. Контекст ускоряет CAD-проверки Store/Read, но не устраняет этот формат и начальную запись меток. Новый frame-путь его не повторяет. Полная заявка на линейное время всего ATTILE была бы недоказанной.

## Артефакты и команды

`source_manifest.json` — исходная ревизия и SHA-256 производственных файлов. `QuantityStorePerfCheck.cs` и `instrument_doubles.py` — самостоятельный runner и точная инструментализация doubles. `z*_p*.json` — структурированные исходные результаты; `.log` — вывод процесса при наличии.

Пример: `source /workspace/scratch/ba306982747c/verification_deps/env.sh`, затем `mono QuantityStorePerfCheck.exe 100 300 fixtures.json z100_p300.json` из каталога baseline. Сборка: `mcs -nologo -r:System.Web.Extensions.dll -main:QuantityStorePerfCheck -out:QuantityStorePerfCheck.exe *.cs`.

В репозитории добавлен обязательный быстрый gate `tools/quantities_3009/test_quantity_store_perf.py --quick`, проверяющий линейную верхнюю границу числа CAD-проверок и единственный ModelSpace scan. Время не используется как нестабильный CI-критерий. Живой AutoCAD остаётся отдельным этапом после ревизии.

Память относится ко всему процессу синтетической фикстуры: CAD doubles и исходный DTO построения остаются в managed-памяти вместе со считываемым паспортом. Это не изолированная стоимость Read и не замер нативной базы AutoCAD; в настоящем отдельном вызове ATFTABLE распределение managed/native памяти будет иным.
