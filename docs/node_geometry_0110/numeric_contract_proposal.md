# 2Б3: точная десятичная граница min20 без допуска

01.10.2026. Read-only проектирование; продукт не изменён, допуска CI на реализацию ещё нет.

## Воспроизведение

Для десятичных заявленных значений нельзя сравнивать результат двоичного `double` суммирования с 20: два явно заданных примера дают ложный отказ.

| Заявленные слои, мм | X ГП, мм | Обычная double-разность | Точная десятичная разность заявлений | Ожидание |
|---|---:|---:|---:|---|
| 108,95 + 53,34 | 182,29 | 19,99999999999997 | 20,00 | PASS локального min20 |
| 85,03 + 37,89 | 142,92 | 19,999999999999986 | 20,00 | PASS локального min20 |
| 85 + 37,64 | 142,64 | 19,999999999999986 | 20,00 | PASS локального min20 |
| 150 | nextDown(170) = 169,99999999999997 | 19,99999999999997 | 19,99999999999997 | FAIL |
| 150 | 170 | 20 | 20 | PASS |
| 150 | nextUp(170) = 170,00000000000003 | 20,00000000000003 | 20,00000000000003 | PASS |
| 150 | 169,999 | 19,998999999999995 | 19,999 | FAIL |
| 150 | 170,001 | 20,001000000000005 | 20,001 | PASS |

Первые две строки и nextDown имеют практически одинаковый двоичный результат, но различный математический смысл десятичных заявлений. Epsilon, округление перед сравнением и `(decimal)double` не решают задачу: cast способен превратить nextDown(170) в 170 и дать ложный PASS.

## Рекомендуемый способ: общая точная десятичная шкала

Старые DTO остаются double. В новом чистом ядре определяется **численный смысл заявленного DTO**: конечное double преобразуется в проверяемое invariant round-trip десятичное представление. Например, `108.95` и `53.34`, а не 17-значные следы двоичного приближения. Затем размерная цепочка исполняется точно в десятичной арифметике. Это не инженерный допуск и не попытка получить истинную физическую точность из введённых чисел.

1. Получить `value.ToString("R", InvariantCulture)` и проверить обратный parse побитовым совпадением конечного double. Если платформа нарушила round-trip — технический отказ, а не замена ближайшим числом. Проверить одинаковые эталоны на Mono и .NET Framework Windows. Не заменять R безусловным G17: для `53.34` G17 даёт `53.340000000000003` и возвращает исходную проблему.
2. Разобрать строку в decimal через `TryParse(... NumberStyles.Float, InvariantCulture)`. Недостаточно одного успеха TryParse: он способен округлять. Сравнить **точное численное десятичное значение** исходной строки со значением parsed decimal, представленным G29. Сравнение — нормализация знака, цифр, десятичного показателя, ведущих/замыкающих нулей; никаких floating операций. Если представления различаются — технический отказ.
3. Для всех участвующих координат и толщин определить максимальный scale S из decimal.GetBits. Привести их к общим целым коэффициентам: `coefficient = new decimal(bits[0], bits[1], bits[2], false, 0)`; умножить coefficient на `10^(S-scale)` **с целым scale=0**. Это точное целое decimal умножение, либо OverflowException: округления дробной части здесь уже нет.
4. Суммировать слои и вычислять разности исключительно над такими целыми коэффициентами. Их scale=0 сохраняется, поэтому любая потеря значащих цифр невозможна: переполнение даёт отдельный технический отказ. Отрицательная разность остаётся точным signed coefficient.
5. Для сравнения и объяснения делить итоговый коэффициент на `10^S`. Это точно представимое decimal с scale <= 28: сравнивать его с decimal 20 без допуска. Можно сравнивать коэффициенты, но умножение константы 20 на `10^S` не должно само приводить к ненужному overflow на S=28; десятичное сравнение после точного восстановления проще.
6. Только координаты для CAD и совместимые публичные числовые поля результата переводить в double. Для каждой пары **различных точных плоскостей**, слившихся в одно double, дать `E_NODE_CAD_PRECISION`; такая схема не рисуется как будто слоя нет. Проверка O(L): dictionary<double, exactCoefficient>, одинаковые exact-плоскости разрешены. Нулевой или отрицательный фактический слой и общий overlap уже проверяются отдельно.

Этот метод использует штатный System.Decimal, без System.Numerics, BigInteger, дополнительной библиотеки или отдельного процесса. Он намеренно отказывает входам, чья совместная десятичная точность превышает представимость backend, даже если отдельные числа представимы. Для инженерно обычных миллиметров и граничных nextDown/nextUp вычисления точны; при необычных размерах с 28 знаками нельзя молча менять заявленное число.

## Техническая область и точные отказы

| Случай | Поведение |
|---|---|
| Не finite / не положительная обязательная координата / неверный тип | Прежний форматный отказ |
| Значение меньше минимальной ненулевой decimal величины 1e-28 или больше Decimal.MaxValue | `E_NODE_NUMERIC_RANGE`, техническая представимость, без инженерного вывода |
| Parse округлил вход, даже если обратный double всё ещё совпадает | `E_NODE_NUMERIC_PRECISION`, исходное точное десятичное заявление не сохранено |
| Все значения по отдельности decimal, но переход на общую шкалу или сумма коэффициентов переполнились | `E_NODE_NUMERIC_PRECISION`, совместная точность цепочки не представима |
| Различные точные плоскости при передаче в CAD стали равными double | `E_NODE_CAD_PRECISION`, слой/просвет нельзя верно изобразить выбранным CAD-представлением |
| Точная разность < 20 | Инженерный `local_clearance=fail`; это не техническая ошибка |
| Точная разность = 20 | Локальный PASS; никакой tolerance не добавлен |

Decimal.MaxValue = 79228162514264337593543950335; это предел численного типа, не максимальный вынос фасада. Общая шкала дополнительно ограничивает произведение `максимальная координата × 10^S`, а не одну универсальную длину. Например, набор `1e20` и `1e-28` отказывается как непредставимый с общей точностью. Не записывать эти числа в каталог изделий, нормы, UI-рекомендации или конструктивные ограничения.

`1e-28` отдельно может быть представимо; оно не обещает, что набор с большой координатой и такой точностью будет принят. Избыточная точность не округляется скрыто. На этом этапе не предполагается проектировать субмикронные слои; сообщение пользователю называет численное ограничение и просит проверить исходные данные, не подменяет их.

## Отображение обязано следовать точной проверке

Из вычисленного decimal хранить точный короткий invariant текст с удалением только незначащих конечных нулей. Для gap и dimension labels не использовать `double.ToString("0.###")` или округление до целых. Точный отказ 19,99999999999997 должен так и отображаться, а не как «20 мм < 20 мм».

Небольшое предлагаемое расширение API перед реализацией:

```csharp
FrameNodeGeometryResult.GapText // null если не рассчитан; exact invariant number
FrameNodeDimension.ValueText  // точное десятичное значение без суффикса мм
```

Публичные GapMm/ValueMm остаются double для совместимости адаптера, но подпись ReviewText и renderer берут GapText/ValueText. Все размерные подписи выводят собственный точный результат ядра. Если после double-конвертации точный gap стал ровно20, а десятичный gap меньше20, статус всё равно FAIL и текст остаётся точным; вставка запрещена. Никакой слой не получает зелёную геометрию из-за округлённой подписи.

Численный способ фиксируется в AlgorithmRevision (либо отдельном неизменяемом numeric_semantics в новом result). Это не меняет solution_selection/catalog_revision/13 paths. Snapshot на другом runtime пересчитывает ту же точную цепочку; golden fixtures обязаны совпадать по статусам, точным текстам и digest.

## Проверки до принятия реализации

- Все восемь строк таблицы; nextDown создаётся через BitConverter по соседнему IEEE754 представлению, не через приблизительное `170 - 1e-14`.
- 0,1 + 0,2; несколько десятков десятичных слоёв; итоговая сумма до/на/после наружной плоскости.
- Два одинаковых смысла с разными десятичными форматами после DTO parse дают один результат; parser не принимает bool/string за number.
- Boundary decimal Parse: 1e-28, 1e-29, Decimal.MaxValue-соседние конечные double; значения, требующие scale>28; значение, которое Parse округлил без overflow.
- Scale alignment и integer sum overflow: каждый даёт отдельный технический отказ; исходный проект/зона не изменены.
- `1e15 + 0.01` как два слоя: decimal-chain точна, но distinct границы сливаются в double — CAD precision отказ, не потерянный тонкий слой.
- Подписи на nextDown и на точном20, decimal pair preflights. Никакого «20 мм» при точном отказе только из-за округления.
- Линейность: одна подготовка числа/scale на операцию; максимум несколько проходов по L; нет повторного суммирования префикса для каждого слоя.

## Альтернатива, если позже потребуется более широкий численный домен

Exact base10 coefficient/scale на BigInteger допускает все конечные double round-trip заявления, без диапазона decimal. Размер коэффициентов ограничивается exponent исходного double и числом слоёв; расчёт также можно сделать O(L). Это новая зависимость/реализация, не обязательная для первого пилота. Она не отменяет последнюю проверку представимости различающихся плоскостей в CAD double и не решает точность реальных исходных измерений. На первом инкременте предпочтителен более узкий проверяемый backend с явным отказом.
