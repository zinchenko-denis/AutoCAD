## Уточнение Германа: настоящая библиотека узлов

Денис 06.10 явно поручил реализовать эту идею после проверки программы,
сначала на одном примере. Это разрешение начать конкретную новую функцию,
несмотря на прежнюю паузу расширения; оно не разрешает сразу все системы.

Смысл сообщения Германа сохранён без исправления его инженерного замысла:

- Нужен отдельный DWG — библиотека типовых узлов разных подсистем из
  альбомов технических решений: вертикальных, межэтажных, ортогональных,
  примыканий, отливов и других повторяющихся решений.
- Узлы представлены динамическими блоками. Инженер вызывает команду,
  вводит толщину утеплителя, вынос облицовки, выбранный кронштейн,
  профиль и другие относящиеся к узлу параметры.
- Затем рамкой/выбором указывает нужные узлы, например три экземпляра.
  В выбранных меняются геометрия, размеры и обозначения деталей;
  невыбранные сохраняются. Из библиотеки инженер собирает проект.
- Толщина из теплотехнического расчёта и проектный вынос — исходные
  данные инженера. Программа не должна заново требовать весь расчёт,
  чтобы графически изменить явно заданные параметры.
- В будущем нужны удлинители кронштейнов, разные профили и фасонные
  элементы. Развёртки зависят от собственных исходных данных и не являются
  обязательной частью первого примера.
- Числа 230/130/330/180 в устном пояснении показывают желаемую динамику,
  но не задают точную формулу или допустимые размеры изделия.

**Текущий ATFNODE этого не реализует.** Он рисует линии/подписи слоёв в
обычном `AFNODE_SCHEMA_*` блоке; его renderer отвергает динамические блоки
и дополнительные атрибуты. Не менять этот опубликованный формат молча.
ATFZONEPARAMS работает с фасадными зонами, а рамка выбора библиотечных
узлов — другое действие; не навязывать зоне роль обязательного владельца.
В продукте есть изменение свойств существующих динамических вставок,
но нет создания библиотеки параметров/действий узла. В публичном репозитории
нужный DWG не найден; наличие пригодного DWG в приватном архиве ещё проверить.

## Первый рабочий пример и критерий завершения

Предпочтительный пилот — уже изученный **Вектор-1 2015, тип 1,
керамогранит, узел 4.2.1, КР2–ПП–УК–ГП**. Не расширять альбомы до
доказанного результата. Сначала инвентаризировать имеющиеся исходники,
затем показать изменение одного настоящего узла, а не новой схемы слоёв.

Основной первоисточник:
`atspec-testdata/docs/facades_atr/ATR_Vector1_3.15_KG_KP_2015.pdf`.
Каталог: `Common/catalogs/vector1_2015_type1_historical.json`.
Приватные DWG/расчёты/оригиналы не переносить в публичный репозиторий;
создаваемую библиотеку с геометрией приватных исходников хранить приватно,
публично — код, минимальные обезличенные примеры и ссылки на источники.

Сначала проверь технический способ создания/импорта нативного динамического
определения для AutoCAD 2024 по официальным возможностям API. Доступ к
`DynamicBlockReferenceProperty.Value` сам по себе не создаёт параметры
и действия. Не обещай конвертацию PDF→динамический DWG до этой проверки.
Если готового определения нет, подготовка первого входит в задачу.
Обычный блок, который перерисовывает плагин, не выдавать за динамический.
При конкретном ограничении среды доведи доступную реализацию до проверяемого
результата и назови оставшийся нативный шаг; не уходи в очередную серию
«паспортов» и общих требований «подтвердить монтажный вариант».

Приёмка первого примера:

1. Один библиотечный DWG, один узел и пять его экземпляров. Изменяются
   выбранные три; два остальных, другие узлы и чужие определения неизменны.
2. Есть штатные динамические свойства блока. Утеплитель, вынос, выбранные
   изделия, связанные размеры и марки меняются согласованно и по явным базам.
3. Два набора параметров, обратный переход и повтор не накапливают сдвигов.
   Сохраняются базовая точка, атрибуты и явно поддерживаемые повороты/масштабы.
4. Отмена/ошибка не оставляет скрытого частичного результата. Совместимость
   выбранных вставок проверяется до записи; запись согласованной группы атомарна.
5. Проверяются COPY, Undo и save/open. Нативные свойства/ручки и вычислитель
   динамики должны быть проверены в AutoCAD 2024; doubles отдельно от host-проверки.
6. Есть понятная команда в интерфейсе и короткий пример «до/после».
   Массовая оцифровка и новые семейства — после проверки этого примера Германом.

Не редактировать общее BlockTableRecord так, чтобы изменились невыбранные
вставки. Имя чужого блока не доказывает совместимость при импорте.
Отличать исходное динамическое определение от анонимного вычисленного
состояния; свойства привязывать явно, не по эвристике «самое большое число».
Новая несовместимая редакция определения требует явного различения версий.

Номинальные базы КР2 известны; полный допустимый перехлёст и ход КР2–УК
не подтверждены. Это ограничивает автоматический монтажный подбор,
но не запрещает изменение графики по явно введённым параметрам.
Дискретное изделие нельзя произвольно растягивать и автоматически маркировать
как допустимый товар. Не выдумывать длины/крепёж/заделку/сечения/припуски гиба.
Изменение выноса не доказывает такое же изменение длины кронштейна.

## Скорость, порядок и следующий выпуск

Не менять `main`, `ATableSpec/`, `ABlockGen/`. Исходники и существенные
решения сохранять в рабочую ветку. Слияние main — только «Пушим».
Один снимок выбранных данных, индексы, пакетная запись; CAD API не выносить
в фон и не обходить весь DWG при каждом поле/реакторе. Замерять чтение,
расчёт, отрисовку и запись отдельно; время Python не равно скорости AutoCAD.
Не раздувать FrameCommand новым независимым модулем библиотеки узлов.

В Git — код, минимальный воспроизводимый вход, необходимые тесты и краткий
итог с SHA/CI. Подробные логи/повторные квитанции — артефакты CI или временно
вне Git. CLAUDE остаётся правилами, статус меняется только в CURRENT_MILESTONES.
Исторический архив docs и старые датированные папки тестов ещё не убраны;
не называть уборку завершённой и не начинать массовую миграцию попутно.
Коммиты по-русски с реальной московской датой. Не придумывать новые вехи
