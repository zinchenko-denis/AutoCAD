## Тот же единственный пилот и его ограничения

Вектор-1 2015, тип1, керамогранит, узел4.2.1, КР2–ПП–УК–ГП.
Физический УК и два подтверждённых интерфейса не назначены; совпадение
марок/координат не доказывает монтажную связь, кинематику или грузовой путь.
Номинальные базы0/2/2+L и неизвестный h сохраняются; min30 других узлов
и165−80=85 не дают полного хода регулировки пилота. НагрузкаL1 не задаёт
реакции всех связей. П2–П4, полный2В и подтверждённый3А остаются BLOCKED;
`physical_assignment=not_asserted`, `MountingStatus=not_confirmed`,
`AutomaticBracketSelectionAllowed=false`, `E_SOLUTION_CALC_UNCONFIRMED`.

Q-01…Q-06 и2А находятся в последнем установочном build-104. Более поздние
2Б1…2Б5,2В1…2В3 и приёмочные изменения находятся в Git после выпуска.
Нового установочного комплекта нет без новой команды Дениса «Собираем».
Живой AutoCAD не проверен; main, ATableSpec и ABlockGen не менять.

пилота либо отдельного изменения цели Денисом.

## Что закрыл предшествующий и текущий проход

Ограниченный П1/П5 использует две отдельные стены1210×1820, плиту600×600,
шов10, ручной каркас800/800. Настоящие settings/guards/движки/producer/store
и модели ведомостей связаны одним persistent процессом/DB CAD doubles.
Данные фиксируются до расчёта; нельзя прикрепить свежие зависимости к
старому ответу. Отдельные операции по зонам сохраняют области свежести.
Эталон12 плит/4,32м²,2ГП/3,64м,6 условных кронштейнов. Проект230→240
устаревает оба каркаса; исключение260 справа — только правый run.
Сопоставляй зоны по контурам/геометрии, не порядковому номеру ответа.

Предыдущий4edc342 также исправил Esc ручных осей ATFRAME до расчёта/CAD;
Enter сохраняет путь завершения списка. Его отдельный axis-test1200×3000
даёт1ГП/4 кронштейна, не смешивать с основнымfixture и humanroute.

Текущий этап исполняет настоящую FacadeQuantityTableCommand.Run
на тех же источниках, а не только напрямую собирать табличные модели.
Сюда относятся новая/обновляемая Table, второй просмотр, свежая проверка
источников перед записью, метаданные владельца и реальные файлы XLSX.
Host/редактор/формы и Table API остаются ограниченными doubles; helpers
ZoneCommand извлекаются дословно. У прежнего no-op hook исходные
проверки limited pilot должны оставаться рабочими.

Отдельный дефект координат: новую точку managed GetPoint надо преобразовать
из текущей ПСК в МСК ровно один раз; Table.Position уже находится в МСК.
ПСК origin(100,200), rotation+90°, точка(3,4) → (96,203) МСК.
При Update прежнюю позицию повторно не преобразовывать. Ориентация
таблицы прежняя, автоматический поворот всей таблицы не введён.
Изменившаяся ПСК должна отклоняться до первой записи. ОснованиеAPI —
официальный managed C# пример Autodesk, не ActiveX Utility.GetPoint;
первичные ссылки — `table_lifecycle_0110/api_coordinate_basis.md`.

## Честные границы следующего шага

Command adapters не являются запущенным AutoCAD. Fill на модели ячеек
не доказывает native Table rendering. Прежний raw metadata stamp таблицы
не проверяет все ручные изменения её ячеек; не обещать защиту всего тела.
Отказ до записи отличается от rollback: QuantityCadDoubles Commit/Dispose
пустые. Отмена посреди Fill, Undo, native COPY/remapping, SaveAs и
DWG save/close/open требуют отдельного host прохода. XLSX файловый rollback
не является доказательством отката CAD-транзакции.

Следующий программный участок — интеграция настоящих ATFNODE
command/store/renderer с общими реальными guards/источниками того же
fixture. Существующий NodeCadProbe исполняет продукт, но подменяет guard.
В QuantityCadDoubles.Add пока все Entity попадают в ModelSpace: простое
подключение renderer ошибочно отнесёт туда и примитивы определения узла.
Сначала воспроизвести конкретный пробел и обосновать минимальную модель
владения. Не вводить полную имитацию AutoCAD ради зелёного счётчика.

Зафиксированный сценарий: N1 создана → проект изменён → попытка N2
отменена/отклонена → N1 сохраняет владельца/определение/паспорт/тело,
остаётся stale → успешная N2 имеет отдельного владельца и fresh,
N1 остаётся stale. Подробности и источники — `next_node_gap.md`.
Подтверждённого дефекта продукта Node заранее не заявлено.
После этого — оставшиеся проверки П5 и живая приёмка по плану;
положительные software тесты не закрывают инженерные М2–М7.

## Скорость, проверки и GitHub

Один проверенный DTO-снимок на фазу операции, индексы ID/ссылок;
CAD API не использовать в чистом расчёте/фоне. Не добавлять ModelSpace scan
и пересчёт из реактора. Кеш не переносить через диалог или изменение DWG.
Сравнивать счётчики на одном входе и время отдельных стадий. Managed
стенд не является замером производительности AutoCAD. Проверка ПСК —
фиксированная матрица, без новых чтений объектов/паспортов источников.
У новой вставки добавлены три чтения Editor.CurrentUserCoordinateSystem
(перед точкой, после и перед записью); не объявлять это отсутствием любых
обращений к CAD API. У обновления и XLSX-only новых чтений ПСК нет.

Перед кодовым коммитом: конкретное before-воспроизведение, регрессия,
весь актуальный набор CLAUDE, compile3, независимая ревизия и проверка
применимости руководства. Полные8 synth/roles можно переиспользовать
лишь после точной сверки44 зависимостей; table command и общие doubles
в них не входят, поэтому обязательные общие проверки всё равно повторяются.
Затем Windows check точного SHA, скачивание/сверка затронутого артефакта
и просмотр изменённых UI. Не приписывать новый визуальный просмотр
неизменённым формам. Прежние snapshots PENDING описывают момент до CI;
итоговый `github_publication.json` фиксирует действительный результат.

Публикация — подключённый GitHub API, проверка удалённого родителя
непосредственно перед fast-forward, force=false; git fetch доступен.

(в том числе CRLF), хеши, причины/ограничения, измерения и промт.
Частные оригиналы/рендеры и секреты в публичный repo не класть.
Продуктовый коммит и последующий docs-only receipt различать явно.
