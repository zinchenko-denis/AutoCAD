# Правила разработки AutoCAD

Общаться по-русски и простыми словами. Заказчик — Денис Зинченко,
инженер фасадного направления — Герман. Сначала проверить числа, затем
сообщать их. Различать исправление программы, проверку и инженерное допущение.

## Начало работы

1. Проверить фактическую удалённую ветку `feat/auto-reactor` и локальные изменения.
   Не сбрасывать новые коммиты, не перезаписывать чужую работу и не делать force-push.
2. Прочитать [текущий план](docs/CURRENT_MILESTONES.md). Это единственное место
   текущего статуса и следующего шага. Модульные `docs/NEXT.md` и handoff — история.
3. Для конкретного дефекта прочитать соответствующий код, контракт и историю решения.
   Начинать с воспроизведения, заканчивать наблюдаемым результатом для инженера.

## Область работы и ограничения

- Фасадные модули: `Facades/` — зоны и ведомости, `AClad/` — облицовка,
  `AFrame/` — подсистема. Общая инфраструктура — `Common/`.
- `main`, `ATableSpec/` и `ABlockGen/` не менять без прямой команды Дениса.
  Слияние в `main` — только по команде «Пушим»; новый установочный выпуск —
  только по новой команде «Собираем». Публикация исходников в рабочую ветку
  входит в задачу сохранения прогресса и не означает выпуск установщика.
- До приёмки согласованного пилота не расширять каталог на новые системы
  и СФТК без изменения задачи Денисом. Область пилота и оставшиеся работы — в текущем плане.
- Перед вопросом Герману проверить ТЗ, альбомы и расчёты в приватном
  `zinchenko-denis/atspec-testdata`, а также `Facades/docs/kb/`.
  Не просить заново уже имеющиеся сведения. Не выдумывать характеристики,
  крепёж, закрепления, монтажные размеры и диапазоны регулировки.
- Исторический выбор изделия и геометрическое соседство не подтверждают
  установленное изделие, физическую связь, неподвижную/подвижную опору или стык.
  Каталожный габарит не заменяет расчётное сечение, вынос облицовки — плечо нагрузки.
- Ответы на инженерные вопросы не блокируют тест уже существующих программных функций.
  Новое продуктовое ограничение объяснять через его влияние на реальный фасад.

## Скорость и сохранность данных

- Чистое ядро получает DTO. CAD API не использовать в циклах расчётных вариантов
  и фоновых потоках. Не запускать полный пересчёт/обход DWG из реактора.
- Один проверенный снимок данных на фазу, индексы вместо поиска для каждой детали,
  пакетная запись. Кеш не переносить через диалог или изменение DWG.
- Сохранять прототипы, пакетное клонирование и неассоциативные заливки.
  История проблем скорости — `AClad/docs/NEXT.md`, записи 26.09b/c.
- Не дублировать геометрию и вложенную строковую сериализацию в паспортах.
  Общие источники хранить один раз; старые опубликованные форматы читать совместимо.
  COPY и повреждённые ссылки не принимать автоматически ради скорости.
- Схема ATFNODE не является физической деталью ведомости. Для неё достаточно
  собственных блока, определения, зоны и проекта; полный обход ModelSpace не нужен.
- Измерять извлечение CAD, расчёт, отрисовку и запись отдельно. Время стенда
  не выдавать за время AutoCAD; сообщения и замеры выводить одной сводкой.

## Проверка и публикация

- Обязательные команды, компиляция и Windows CI — [docs/TESTING.md](docs/TESTING.md).
  Ошибку сначала воспроизвести; для исправления добавить необходимую регрессию.
  Успешный CI и CAD doubles не заменяют живой AutoCAD.
- Проверять затронутый пользовательский путь и удобство результата. Не начинать
  новые искусственные этапы после того, как поставленная задача уже проверена.
- Перед передачей очередного комплекта конструктору обязателен выполненный
  сценарий в полном AutoCAD 2024 на проверяемых DLL/LISP и входных DWG.
  Отсутствующий host, пропущенный шаг и отказ обычного сценария не являются PASS.
  Компиляция, doubles и отдельная нативная проба адаптера не закрывают весь
  пользовательский путь; матрица и границы — в `docs/TESTING.md`.
  Явное поручение Дениса выпустить комплект для нативной проверки Германом
  разрешает такой проверочный выпуск с незакрытой нативной приёмкой; это
  не разрешение называть невыполненные сценарии успешными.
- Сборку запускать штатным `workflow_dispatch` на рабочей ветке. Если операция
  недоступна, выяснить фактический доступ; не переносить ограничения старой среды.
- Установочный выпуск проверять скачиванием `build-N` и `latest`: состав,
  исходный SHA, DLL/движки и совпадение архивов. Три фасадных бандла обновляются вместе.
  Исправление в Git само по себе не исправляет ранее выданный установщик.
- Публиковать короткий итог: пункт плана, изменение для пользователя, проверки,
  ограничения и следующее действие. Текущий статус обновлять только в текущем плане;
  из остальных точек входа давать ссылку. Подробные новые логи — в артефактах CI.
- Коммиты: `<область> (ДД.ММ): что сделано`, по-русски, с фактической датой.
  Сохранить причину дефекта и проверенный коммит; не копировать отчёт во все журналы.
- Токены и пароли никогда не писать в файлы, коммиты и логи. Рабочие DWG,
  расчёты и оригиналы альбомов хранить приватно. Отделу пишет сам Денис.
- Для необходимых GitHub-действий без API ранее разрешён браузерный доступ.
  Не запрашивать повторное согласие на тот же переход; авторизацию и защиту
  аккаунта не обходить. Ошибку CI сначала сопоставить с run ID и SHA.
